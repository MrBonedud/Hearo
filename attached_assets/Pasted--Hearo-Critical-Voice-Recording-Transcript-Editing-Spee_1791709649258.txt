# Hearo — Critical Voice Recording, Transcript Editing & Speech Recognition Bug Fix

You are working on the existing Hearo / Listen First application. This is a critical usability issue that must be fixed before the upcoming presentation.

Do not merely inspect the code and suggest solutions. Investigate the actual implementation, reproduce the issue, fix the root cause, and verify the complete voice-recording workflow in the running application.

## 1. The reported bug

When a learner records their voice and speaks, they may notice that they misspoke or used the wrong word. They want to edit that specific word in the transcript.

Currently, editing the spoken text can cause the transcript to become corrupted, mixed up, overwritten, or incorrectly interpreted. Instead of correcting one word, the learner may lose or disturb other parts of the transcript.

This makes the voice-based learning experience unreliable.

**The expected behavior is simple: recording a response, editing one word, and continuing should never unexpectedly destroy, replace, reorder, or corrupt the rest of the transcript.**

First, reproduce this behavior in the current application. Do not assume the implementation uses a particular speech recognition API or transcription architecture. Inspect the actual code and determine what is happening.

## 2. Trace the entire voice-to-transcript workflow

Inspect all relevant components, hooks, state, and event handlers involved in:

- Starting and stopping a recording.
- Receiving microphone audio.
- Speech recognition and transcription.
- Handling interim and final recognition results.
- Displaying the transcript.
- Editing the transcript manually.
- Saving or updating the edited text.
- Resuming recording after editing, if supported.
- Submitting the response for evaluation.
- Generating and displaying assessment results.

Identify the actual source of the corruption.

Investigate possible causes, including:

- Speech recognition results overwriting manually edited text.
- Interim transcription results replacing previously finalized text.
- Repeated recognition events appending the same words multiple times.
- Stale React state or stale closures.
- Incorrect state synchronization between the audio recorder, speech recognition hook, and transcript editor.
- Multiple event listeners or recognition sessions running simultaneously.
- Incorrect use of `onresult`, `onend`, `onerror`, or equivalent callbacks.
- Incorrect transcript concatenation or replacement logic.
- Controlled input values being reset during re-rendering.
- Textarea cursor position or selection being lost during updates.
- Recording being restarted without preserving the existing transcript.
- Edited text being replaced by an older transcript stored elsewhere.
- Race conditions between recording events, state updates, and manual edits.
- Duplicate submissions or transcript processing triggered by multiple events.

These are investigation targets, not assumptions. Fix the cause demonstrated by the actual code and reproduction.

## 3. Establish a safe transcript state model

Implement a clear separation between the following concepts wherever the current architecture requires them:

1. **Recognized transcript:** Text produced by speech recognition.
2. **Editable transcript:** The current text displayed to and controlled by the learner.
3. **Final submitted transcript:** The exact text submitted for assessment.

Do not allow incoming speech recognition events to silently overwrite manually edited text.

Use a single, clearly defined source of truth for the editable transcript. Avoid multiple independent state variables that continuously overwrite each other.

If the application supports interim and final recognition results, handle them separately and consistently. Do not treat every recognition event as a completely new transcript.

Preserve the existing architecture where practical. Do not introduce unnecessary state-management libraries or rewrite unrelated parts of the application.

### Required data integrity rules

- Existing transcript text must not disappear because of a new recognition event.
- A manually corrected word must not be replaced by an older recognition result.
- Repeated recognition events must not duplicate previously accepted words.
- The text must remain in the correct order.
- Editing one part of the transcript must preserve the rest.
- The final submitted text must match the text the learner actually sees and intends to submit.
- A failed recording or recognition event must not erase existing text.
- The application must not silently reset the transcript when recording starts or stops.

If the learner intentionally clears or replaces the transcript, respect that explicit action.

## 4. Make manual transcript editing reliable

Inspect the existing transcript editing UI and fix any problems that interfere with normal text editing.

The learner must be able to:

- Click anywhere in the transcript.
- Correct a misspelled or incorrectly recognized word.
- Insert or delete words.
- Edit a sentence without changing unrelated sentences.
- Select and replace a specific portion of text.
- Use Backspace, Delete, arrow keys, Ctrl+A, copy, paste, and undo where supported by the browser.
- Move the cursor normally without it unexpectedly jumping to the end.
- Continue editing while the component re-renders.
- Preserve line breaks and normal spacing.

Do not re-render or reset the editor value unnecessarily while the learner types.

If the transcript editor is a controlled React input or textarea, ensure that its value and change handler are correctly synchronized and that asynchronous recognition updates do not reset the current editing session.

Do not automatically replace the user's current editing value with a fresh recognition result.

Do not add a complicated new workflow unless it is necessary.

If resuming recording after manual edits is supported, ensure that new recognized speech is integrated without replacing previously edited content or duplicating earlier speech.

If the existing implementation cannot safely merge resumed speech into manually edited text, use an explicit and understandable transition rather than guessing where the new speech belongs.
